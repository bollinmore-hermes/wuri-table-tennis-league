# Direct public data publication (Test)

## Contract
Test public data updates no longer dispatch GitHub Actions. Authenticated admins call `publish-public-snapshot`; the server freezes the curated/masked schema-one payload and hash in a shared-lock reservation, uploads a request/hash-specific immutable JSON object, anonymously reads it back, verifies shape/digests/identity, and atomically confirms the current pointer and verified hash. Only this receipt permits a `published` result. Program deployments still use Actions. Production promotion explicitly enables `PUBLIC_SNAPSHOT_DELIVERY=storage` at the tag-only build step; database/Edge activation is a separate approved operation.

The public browser reads an anonymous no-store Edge pointer (small service-only RPC projection), then the referenced immutable object. It does not authenticate or read raw league tables. Credentials never enter the public artifact. Pointer URLs, object paths, project/season, schema, receipt, content hash and snapshot digest are validated. A schema-one data receipt may predate a compatible program deployment: its commit/tag is data provenance, never a selector capable of replacing application code. Static fallback still pins the exact deployed program source. Never carry this compatibility assumption across a schema change.

Each successful pointer switch is a data-publication event, not an application release. The UI reports the operation complete only after confirmation; opening an already-loaded public page requires refresh. There is no fixed-second SLA. Storage reads/Edge metadata calls incur Supabase usage. Immutable objects retain cacheable long-lived paths; the no-store pointer also uses a cache-busting query. No realtime subscriptions/public polling were added.

## Failure and concurrency
Manual and automatic reservations use the existing global publication lock, authoritative hash and pending-row checks. Actions reservations are denied after the delivery switch. Direct publications have no Actions-specific one-minute cooldown, but pending/unknown requests still block duplicate work. A later saved edit remains dirty; pending reconciliation may perform at most one immediate follow-up. Unknown write results are reconciled by reading the same object, never by blindly uploading/reserving again. Definite failures retain the old pointer. Retried confirmation cannot roll a newer pointer back. Failure of a post-confirmation metadata refresh cannot downgrade a confirmed row or UI receipt. When latest data reads fail, the public UI labels the static fallback as possibly older, never claims it is current.

## Operations
Migration 013 installs the bucket/service-only control RPCs with `delivery_method=actions` initially; it does not enable direct delivery or alter the existing two-minute job. Deploy Test Edge handlers and Pages before switching the Test row to `storage`, under advisory lock after verifying no pending Actions request. Bootstrap the first Storage pointer from a real validated reservation, not by fabricating a verified hash. Keep migration order and the original applied history.

The public `wuri-public-snapshots` bucket holds JSON only, maximum 2 MB. Existing browser policies are limited to team logos; no browser snapshot-write policy is granted. The Edge pointer's GET is anonymous read-only; privileged SQL RPCs/tables remain service-only. Use metadata/SQL readback and anonymous object verification after every deployment. Do not put service credentials, publication/cron secrets or full Auth sessions in evidence.

Rollback: first resolve any pending/unknown publication; redeploy the last known static-pinned Test artifact, then switch the Test control row back to `actions` under the shared lock. Retain existing immutable snapshots and migration/audit history; deleting history is not necessary. Production rollout requires separate confirmation, migrations and a program tag. Require explicit promotion approval before merging/tagging. For Production create the control row disabled, configure an independent Cron secret/Vault entry, deploy handlers, initialize one verified Storage pointer, and explicitly alter the existing job to `*/2 * * * *`; migration 012 only auto-adjusts the enabled Test job. Enable ongoing automation only after the tagged program/live identity is verified. Never migrate Test records or reseed populated Production. A missing real Production admin session is a separate verification gate, not permission to borrow Test credentials.
